一、一句话定位

FlashOCC 是一篇工程导向的工作：它论证了「很多场景下 3D 算子不是必需的」。做法极简——把高度维折进通道，全程只用 2D 卷积，最后 reshape 成三维。

论文 FlashOcc: Fast and Memory-Efficient Occupancy Prediction via Channel-to-Height Plugin
arXiv 2409.11160（初版 2023-11）
定位 插件式思路，可挂到任意 BEV 检测器上

二、它的判断

稠密体素方法都用 3D 卷积或三维注意力，显存和延迟都吃紧，车端部署困难。FlashOCC 提出一个尖锐的观察：语义占据真正需要的只是「每个平面位置上有哪些高度层被占、各属哪类」，而不是一个连续的三维特征场。

如果这个判断成立，那就可以把 z 轴当成「额外通道」，用 2D 卷积一次性预测出所有高度层——num_classes × Dz 个通道，reshape 即得三维结果。

三、关键技术与源码

3.1 视图变换阶段就把 z collapse 掉

img_view_transformer=dict(
    type='LSSViewTransformer',
    grid_config=grid_config,
    in_channels=256,
    out_channels=numC_Trans,     # 64
    sid=False,
    collapse_z=True,             # ★ 关键

collapse_z=True 意味着 LSS 的深度分布不再分散到 z 维，而是直接沿 z 累加，输出一张干净的 200×200 BEV 特征图。这样后面完全不需要 3D 算子。

3.2 channel-to-height：核心插件

class BEVOCCHead2D(BaseModule):
    def __init__(self, in_dim=256, out_dim=256, Dz=16,
                 num_classes=18, use_predicter=True, ...):
        out_channels = out_dim if use_predicter else num_classes * Dz
        self.final_conv = ConvModule(self.in_dim, out_channels,
                                     kernel_size=3, stride=1, padding=1)

out_channels = num_classes × Dz = 18 × 16 = 288。一次 3×3 卷积把 256 维变成 288 维，然后 view 成 (B, 200, 200, 16, 18)——高度维 16 层凭空出现。

3.3 另一种实现：3D 头的 permute 技巧

class BEVOCCHead3D(BaseModule):
    def forward(self, img_feats):
        # (B, C, Dz, Dy, Dx) --> (B, Dx, Dy, Dz, C)
        occ_pred = self.final_conv(img_feats).permute(0, 4, 3, 2, 1)

两种头并存：2D 版靠通道展开，3D 版靠 permute 转置。它们的区别在于 Dz 是在通道里还是在空间维里，但都避免了真正的三维卷积。

3.4 配置里的实际数值

point_cloud_range = [-51.2, -51.2, -5.0, 51.2, 51.2, 3.0]
grid_config = {

注意 z 的步长 6.4 覆盖了整个 [-1, 5.4] 区间，只有 1 格——这就是 collapse 的量化体现。而最终的 Dz=16 是插件自己设定的高度层数，不是从 grid_config 推导来的。

四、省在哪里，代价是什么

省的：3D 卷积、体素查询、三维注意力——一个都不用。2D 卷积在 TensorRT + FP16 下能跑到很高的帧率。
代价：高度维靠通道隐式承载，跨高度的遮挡关系表达受限。比如悬空的树枝和它下方的地面，在通道维度上只是不同 channel 的数值，模型没有显式的「上下相邻」归纳偏置。
适用边界：语义占据（判断某格属于哪类）足够；但对精细几何（表面法向、薄结构）不如真三维方法。

五、在谱系里的位置

与检测侧的对应：它对应 LSS 那一路「显式深度上抛」的延伸——LSS 本来就把深度分布 splat 到 BEV，FlashOCC 只是接着把高度也折进去。
与 TPVFormer 的关系：两者都在降维，但方向相反。TPVFormer 降到三个平面（每个位置有独立语义），FlashOCC 降到一个平面 + 通道（位置语义在通道里）。
工程价值：它是一篇把「能不能去掉 3D 算子」这个问题穷尽到底的论文，结论对部署很有参考意义。
