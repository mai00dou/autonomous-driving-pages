一、为什么把 OCC 单独拆出来

占据栅格预测（Occupancy Prediction）在车载感知里是一个与 3D 检测并列、但不相同的任务。检测回答「有哪些目标、框在哪」，占据回答「这团空间是空的还是被占的、占了归哪一类」。这个差别决定了它无法沿用检测那套评测：检测看 mAP/NDS，占据看 mIoU 与 rayIoU；检测的真值来自人工标注框，占据的真值要么靠多帧 LiDAR 累积重建，要么干脆没有真值只能自监督。

更实际的理由是规模。此前这部分内容被塞进 DETR→PETR 谱系 deck 的第 51–54 页，只有 4 页、8 篇论文，而手头能核到源码的仓库已经有 13 个。四页的体量既讲不清监督信号从哪来，也放不下各篇点云范围、体素分辨率这些真正决定可比性的参数。

二、表征的四条岔路

所有 OCC 工作的第一个分岔点是：把三维几何绑在什么载体上。这与 3D 检测里的稠密 BEV / 特征侧 3D PE / query / 显式深度四岔口是同构的，只是换到了三维空间。

路1

稠密体素

直接预测一张三维占据栅格，逐体素做多类分类。几何最直白，代价是空格也照样参与计算。

SurroundOcc · OccFormer · PanoOcc

路2

三平面降维

把三维拆成三个互相垂直的二维平面，在平面上做注意力，再交叉查询还原三维。规模骤降，代价是交叉处表达是隐式的。

TPVFormer

路3

稀疏查询

用一组 query 表示一块体积，只在前景处分配算力，靠迭代 refine 逼近几何。算力随内容伸缩，代价是早期收敛慢。

SparseOcc · VoxFormer

路4

通道承载高度

把 z 轴折进通道维，全程只用 2D 卷积，最后 view 成三维。没有 3D 算子，代价是跨高度关系表达受限。

FlashOCC

三、谱系：谁从谁身上长出来

这一支没有检测那边整齐的「DETR → DETR3D → PETR → …」单线，而是四条岔路各自演进、再互相借算子。下面按时间排。

2023 上半年 · 表征定型
TPVFormer（CVPR 2023，2302.07817）提出三平面；SurroundOcc（ICCV 2023，2303.09551）用稠密体素 + 多帧 LiDAR 融合重建真值，把「真值从哪来」这个问题第一次工程化；VoxFormer（CVPR 2023，2302.12251）走两阶段稀疏路线：先出可见部分，再补全被遮挡区域；OccFormer（ICCV 2023，2304.05316）把 Mask2Former 的 mask 查询搬到占据上。
2023 下半年 · 监督与效率
PanoOcc（2306.10013）做全景占据；FlashOCC（2409.11160）用 channel-to-height 把 3D 算子彻底去掉；RenderOcc（CVPR 2024，2309.09502）用体渲染把监督降到 2D 语义/深度，绕开 3D 真值瓶颈；SelfOcc（2311.12754）进一步走到全自监督。
2024 · 稀疏与预测
SparseOcc（CVPR 2024，2312.17118）把 DETR 的一对一匹配搬到实例掩码上，纯稀疏；OccWorld（CVPR 2024，2311.16038）把占据当状态空间做世界模型；GaussianFormer（2405.17429）用 14.4 万个高斯球表示场景；occ-flow（2407.07587）加自监督占据流；FB-BEV（2308.02236）提出前后向视图变换。

四、算力账本：同一个 occ_size，不同的物理尺度

这是最容易写错的一处。多篇论文都写 occ_size=[200,200,16]，但各自的点云范围不同，换算出的体素边长完全不同——直接把 mIoU 拿来横比是没有意义的。

SparseOcc：point_cloud_range=[-40,-40,-1.0,40,40,5.4] → 80×80×6.4 m，occ_size=[200,200,16] → 体素 0.4×0.4×0.4 m
SurroundOcc：[-50,-50,-5.0,50,50,3.0] → 100×100×8 m，[200,200,16] → 体素 0.5×0.5×0.5 m
TPVFormer：[-51.2,-51.2,-5.0,51.2,51.2,3.0] → 102.4×102.4×8 m；但它不建稠密栅格，三个平面 100×100+100×8+100×8 共 11,600 个位置
FlashOCC：grid_config 的 x/y 仍是 [-40,40,0.4]，但 Dz=16 折进通道，前向只有 2D 卷积
OccFormer：occ_size=[256,256,32]，比上面几家都细，却配 100 个 mask 查询——用查询数换分辨率

六、四篇主干深度解读

01

SurroundOcc

稠密体素路线的基准。真正的贡献不是网络结构，而是把稠密真值造出来：多帧 LiDAR 融合 + Poisson 表面重建，这套流程后来成了整个社区的数据基础。

ICCV 2023 · 2303.09551

02

TPVFormer

三平面降维的提出者。100×100×8 的三个平面共 11,600 个位置，用二维注意力承载三维语义，是「最小算力」思路最优雅的一次表达。

CVPR 2023 · 2302.07817

03

SparseOcc

DETR 基因在 OCC 最完整的落地。100 个 query、8 帧采样、掩码级匈牙利匹配（cost_class=2.0, cost_mask=5.0, cost_dice=5.0），前向零稠密体素。

CVPR 2024 · 2312.17118

04

FlashOCC

极致工程化：Dz=16 折进通道，collapse_z=True，全程 2D 卷积，无任何 3D 算子。它证明了 很多场景下 3D 算子不是必需的。

2409.11160

七、与检测谱系的关系

DETR 那三条基因在这里换了载体继续活：匈牙利匹配 → SparseOcc 的实例掩码匹配；deformable 采样 → SurroundOcc 直接改 deformable_attention.num_points 做 2D→3D，SparseBEV 的 SASA/AdaptiveMixing 又被 SparseOcc 原样搬去做体素解码；reference point → query 的 3D 中心，query 不再表示「一个目标」而表示「一块体积」。

完整的检测谱系（14 篇）在 DETR→PETR 谱系 那份 deck 里。
